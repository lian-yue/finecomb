# 4.72 Media streaming, DRM and content delivery

Applies to: video and audio streaming services, signed or tokenized media URLs, DRM license servers, packaging and transcoding pipelines, and the CDN and origin setup that serves media. Apply your own knowledge of the specific streaming protocols, DRM systems and CDNs to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Signed and tokenized URLs** | The signature or token does not cover the path, query, byte range, expiry or client it is meant to limit; a token for one segment or folder also opens others; tokens last too long and can be reused or shared freely; the signing key is shipped to clients (see [4.4](4.4-cryptography-and-credentials.md) ("Secrets shipped to clients")) |
| **License server checks** | The license server hands out content keys without checking the device, the user's entitlement for that exact content, or the number of concurrent streams; keys for higher quality are given to clients that only claim stronger protection; one key protects many titles or all quality levels |
| **Entitlement checked only on the client** | Region, subscription, age, rental window or blackout checks run in the player or app, or only when the playlist is fetched, while segments, keys and other endpoints serve anyone (see [28](../dimensions/28-authorization-and-access-control.md) ("Consistency across entry points")) |
| Playlists and manifests | Manifests and playlists from clients or third parties are trusted; URLs inside them send players, packagers or ad insertion servers to any host (see [4.21](4.21-outbound-requests-and-server-side-request-forgery.md) ("Who decides the destination")); editing a manifest unlocks other renditions, skips ads or swaps key locations |
| Origin exposure and hotlinking | The origin server or storage bucket can be reached directly, skipping the CDN's token checks; other sites embed or proxy the streams; a referrer check is the only protection |
| CDN caching of private media | Private or per-user media, keys and manifests are cached under keys that ignore who asked, so one user's content is served to another; or tokens in the cache key send every request to the origin (see [4.6](4.6-caching-and-storage.md) ("Cache keys and isolation")) |
| **Parsing and transcoding untrusted media** | Uploaded media and subtitles go into decoders and transcoders without size, time or resource limits, without a sandbox, or with more privilege than needed; media formats that reference other files or URLs are followed (see [4.3](4.3-decoding-untrusted-external-data.md) ("External entities and references")) |
