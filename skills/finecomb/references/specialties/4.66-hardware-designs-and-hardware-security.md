# 4.66 Hardware designs and hardware security

Applies to: RTL and HDL code, SoC integration, security IP blocks, boot ROM code and the hardware settings that firmware relies on. Apply your own knowledge of the specific architecture, bus protocol and design tools to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Debug and test access** | JTAG, scan chains, test modes and manufacturing interfaces stay open or unauthenticated in production parts, or the lock can be undone by a reset, a fuse state or a debug request during boot (see [4.36](4.36-embedded-firmware-and-real-time-constraints.md) ("Debug interfaces")) |
| Reset and initial values | Security-relevant registers, state machines and memories come out of reset, wake-up or a partial reset in an unsafe or unknown state; one reset domain leaves protections off while another is already running |
| **Lock bits and write-once registers** | Lock bits, write-once registers and fuse shadows can be changed after they are set, through another bus master, an address alias, debug access or a reset of only part of the chip |
| **Access control in the interconnect** | Security attributes on bus transactions (secure or privileged state, initiator ID) are not set, are lost at bridges and address translation, or are not checked by the target; address decoding has gaps or aliases that reach protected regions; DMA masters skip the checks |
| Secrets not cleared | Keys and other secrets stay in registers, buffers, caches or memory after use, after a mode change or after reset, where debug or a less trusted mode can read them (see [4.4](4.4-cryptography-and-credentials.md) ("Secrets in memory")) |
| Side channels and fault injection | Timing, power, electromagnetic output or shared microarchitectural state (caches, predictors, speculative execution) depends on secrets; a glitch can skip a check because a security decision rests on one bit or one comparison with no redundancy (see [4.4](4.4-cryptography-and-credentials.md) ("Constant time and side channels")) |
| **Boot ROM and secure boot chain** | Boot ROM code, which cannot be patched, parses images, headers or boot media without full checks; signatures do not cover everything that runs; recovery or fallback boot modes skip verification; there is no rollback protection (see [4.36](4.36-embedded-firmware-and-real-time-constraints.md) ("Anti-rollback")) |
