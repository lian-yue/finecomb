# 4.73 Backup, archive and disaster recovery

Applies to: backup software and backup jobs, snapshots, database dumps, archives, and replication and failover set up for disaster recovery. Apply your own knowledge of the specific backup tools, storage services and databases to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Protection of backup copies** | Backups, dumps and snapshots hold the same secrets and personal data as the source, but have weaker access control, no encryption, public or shared storage, or copies in test and developer environments |
| **Who can restore, and to where** | More people can restore, mount, clone or export a backup than can read the source; a restore can go to any host, account or path, or overwrite system files; paths inside the archive are not checked on restore (see [4.8](4.8-file-systems-and-paths.md) ("Archive extraction")) |
| **Deletion and tampering by an admin** | The same admin account or credentials that run production can delete backups, shorten retention, remove locks or encrypt the backups; backup agents on hosts hold credentials that can delete the backup store; no copy is offline or write-once |
| Encryption keys for backups | Keys are stored next to the backups, so encryption protects nothing; or keys live only in the system being protected, so losing it loses every backup; key rotation leaves old backups unreadable |
| Backup agents and their privileges | Agents read and write files with high privilege in places that low-privilege users control, following links they planted (see [4.47](4.47-local-privileged-components-and-local-privilege-escalation.md) ("File operations in low-privilege writable locations")); the agent's control port accepts commands without strong authentication |
| **Restoring old state** | A restore or failover brings back revoked users, old credentials and keys, removed permissions, deleted data or old vulnerable versions; one-time tokens and counters go back and are accepted again (see [facets](../facets.md) "Old valid versions accepted again") |
| Retention and deletion in backups | Data deleted because of a legal duty or a user request stays in backups with no expiry, and comes back on restore (see [30](../dimensions/30-privacy-data-governance-and-compliance.md) ("Whether deletion is real")) |
| Restores tested and consistent | Backups are never test-restored; failed, partial or corrupt backups go unnoticed; backups of related systems restore to points that do not match; replication copies deletion, corruption or encryption straight to the replica, so no clean copy is left (see [25](../dimensions/25-crash-and-recovery.md) ("Backups and drills")) |
