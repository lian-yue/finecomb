# 4.58 Multi-tenant platforms and hosting of user content

Applies to: platforms that serve many customer organizations from shared code and infrastructure, and services that host sites, files or code published by users. Apply your own knowledge of the specific hosting platform, framework and cloud services to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Tenant context everywhere** | The tenant is checked in request handlers but lost, or taken from the payload, in background jobs, caches, search indexes, logs, analytics, exports and admin tools; a missing tenant falls back to a default tenant or to all tenants (see [28](../dimensions/28-authorization-and-access-control.md) ("Multi-tenant boundaries")) |
| Keys and data separation | Tenants share one encryption key, one database role or one storage prefix, separated only by a filter; per-tenant keys exist, but a tenant ID taken from the request selects the key |
| **Custom domains and user subdomains** | Custom domains are not verified again, so a stale record can be claimed by another tenant; cookies set on the parent domain are shared across user subdomains; the platform domain is not on the public suffix list, so user sites can set cookies for each other or count as same-site (see [targets: live services](../targets/live-services.md) ("Dangling DNS and subdomain takeover")) |
| **Origin of user content** | User-uploaded HTML, SVG, scripts or other files are served from the application's origin or from an origin shared by many users, so they run with a viewer's session or read other users' content; content type sniffing turns uploads into pages |
| Tenant-defined code and integrations | Code, webhooks, scripts and integrations defined by one tenant run with shared credentials, or reach internal networks or other tenants' data (see [4.21](4.21-outbound-requests-and-server-side-request-forgery.md) ("Internal network and metadata")) |
| Noisy neighbors | One tenant can use up shared CPU, storage, connections, queues or rate limits so other tenants slow down or fail; limits apply per request or per user rather than per tenant (see [facets](../facets.md) "What a limit is bound to") |
| **Public share links** | Share tokens are short, guessable or never expire; a link grants more than the sharer's own rights, or keeps working after the sharer loses access or the item moves; links leak through referrers or search indexing (see [facets](../facets.md) "Values that must not be guessable") |
| Tenant deletion and offboarding | Deleting a tenant leaves its data in backups, indexes, object storage and caches; its domains, tokens, webhooks and scheduled jobs stay active; its names and IDs are freed for a new tenant, who then receives the old tenant's data (see [30](../dimensions/30-privacy-data-governance-and-compliance.md) ("Whether deletion is real")) |
