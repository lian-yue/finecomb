# 4.54 Sync, collaboration and offline clients

Applies to: real-time collaborative editing, sync engines and protocols, offline-first apps with a local database, replication between clients and servers, CRDTs and operational transformation, and file sync. Apply your own knowledge of the specific sync framework to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Authority stays on the server** | An operation received through sync is accepted because it came through the sync channel, or because it carries a client-supplied author, owner or permission field, instead of being authorized on the server for the current user and object |
| **Operations applied later** | Operations queued while offline are checked against permissions and state from when they were created, not from when they are applied, so changes still land after access was revoked, the object was deleted or the workflow was closed |
| **Merge and conflict rules** | Merging concurrent changes produces a state that no single valid change allows (a duplicated unique value, a broken invariant, a field changed by someone without the right); security-relevant fields are merged as "last writer wins" from the client |
| Deletes and tombstones | Deleted items come back after syncing with an old replica; tombstones expire before every replica has seen them (see [4.6](4.6-caching-and-storage.md) ("Deletion and resurrection")) |
| Identity of changes | Operation IDs, clocks and sequence numbers are not issued or checked by the authoritative side, so one client can forge or reuse another's to overwrite or hide changes |
| Removing members | After a member is removed, new data still syncs to their devices, or their queued changes are still accepted |
| Local data on devices | The local store holds data the user may not see, is not protected at rest, or is not cleared when the user signs out or the account is removed |
| Limits | Document size, history length, number of operations and number of connected clients have no bounds (see [20](../dimensions/20-resource-bounds-and-backpressure.md)) |
