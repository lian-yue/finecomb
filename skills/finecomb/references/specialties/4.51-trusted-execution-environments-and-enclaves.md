# 4.51 Trusted execution environments and enclaves

Applies to: code that runs inside, or talks to, an enclave or trusted execution environment (for example Intel SGX or TDX, AMD SEV-SNP, Arm TrustZone trusted applications, confidential VMs and containers, secure elements), and the host code that loads it. Apply your own knowledge of the specific platform and its known issues to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Data from the untrusted side** | Pointers, lengths, buffers and handles passed in by the host, and values returned by calls out to the host (system calls, file and network results, time), are used inside the boundary without checks: a pointer is not confirmed to point where it should, a length is not bounded, or a host result is trusted because the host "should" behave |
| **Copy before check** | Memory shared with the host is checked in place and read again later, so the host can change it between the check and the use; it should be copied in once and checked on the copy (see [4.30](4.30-os-interfaces-system-calls-and-descriptors.md) ("Reading untrusted memory twice")) |
| Entry points | Not every entry into the boundary (enclave calls, commands, secure monitor calls) is listed and checked; debug or test entries remain in production builds; the enclave is built or signed in debug mode |
| **Sealed and stored state** | Sealed data is not bound to the right identity and version, or the host can roll it back to an older copy; sealing keys are shared between enclaves that should be separate |
| **Attestation binding** | The attestation report is not checked against the expected measurements and security version, is not fresh, or is not bound to the channel or key actually used, so a report from one session can be reused in another (see [4.4](4.4-cryptography-and-credentials.md) ("Remote attestation")) |
| Leakage to the host | Secret-dependent branches, memory access patterns, page faults, error codes or timing that the host can observe; enclave memory returned to the host without being cleared |
| Updates and revocation | A fix does not raise the security version, or verifiers still accept older vulnerable versions (see [facets](../facets.md) "Old valid versions accepted again") |
