# 4.68 Container runtimes and isolation

Applies to: low-level and high-level container runtimes, sandboxed runtimes, and build and image tools that unpack or assemble images. Apply your own knowledge of the specific runtime and the kernel features it uses to each row. For a running cluster see [targets: Kubernetes clusters](../targets/kubernetes-clusters.md); for an image see [targets: container images](../targets/container-images.md).

| Checkpoint | What counts as a problem |
| --- | --- |
| **Namespaces and ID mapping** | The container shares host namespaces it does not need; user namespace ID mappings map container users onto real host users or files; files created inside get host ownership that can be used outside |
| **Mounts and host paths** | Host paths, the runtime's control socket, device nodes, or `/proc` and `/sys` entries are mounted or left writable; mount sources or targets are resolved through links the container controls, so a mount lands outside its intended place (see [4.8](4.8-file-systems-and-paths.md) ("Links and replacement after check")) |
| Restrictions actually applied | Capabilities, seccomp, security module profiles, no-new-privileges and read-only settings are requested but not applied on some paths (exec into a running container, another kernel or platform, a fallback when a feature is missing), or a failure to apply them is ignored |
| **Host descriptors and working directories** | File descriptors, the working directory, environment variables or the runtime binary itself stay reachable from inside the container at start or during exec, which gives a path back to the host (see [4.22](4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md) ("Descriptor leaks")) |
| Host actions inside the container's root | The runtime or host tools read, copy or run files inside the container's root file system (user lookup, copying files in or out, health checks) and follow links or trust contents the container controls |
| **Image unpacking** | Layer entries with links, whiteouts, absolute or `..` paths, device files or special permission bits write outside the root or change existing files; the unpacker runs with more privilege than it needs (see [4.8](4.8-file-systems-and-paths.md) ("Archive extraction")) |
| Resource limits | Memory, CPU, process count, disk, inodes and log output are not limited, so one container starves the host or its neighbors; limits cover the main process but not exec sessions or helpers (see [20](../dimensions/20-resource-bounds-and-backpressure.md)) |
| Privileged helper processes | Shims, daemons, setuid helpers and network plugins that run as root accept requests or files from the container or from unprivileged local users without treating them as untrusted (see [4.47](4.47-local-privileged-components-and-local-privilege-escalation.md)) |
