# 4.69 Package registries and artifact repositories

Applies to: the server side of package and artifact hosting (public and private package registries, artifact repositories, container registries) and the proxies, mirrors and caches in front of them. Apply your own knowledge of the specific ecosystem and its package formats to each row. To review a package that users install, see [targets: published packages](../targets/published-packages.md).

| Checkpoint | What counts as a problem |
| --- | --- |
| **Namespace ownership and reuse** | Ownership of a name, scope or organization is granted loosely; transfers, account recovery or lapsed maintainer email domains let someone take over a name; a deleted or renamed name can be registered by someone else and receives its old users' installs (see [36](../dimensions/36-supply-chain-and-artifact-integrity.md) ("Names re-registered after they lapse")) |
| **Publish authentication** | Publish tokens are long-lived, broad or not bound to a package; a second factor is not required to publish; trusted publishing accepts identity tokens from any repository, workflow or branch that matches a loose rule |
| Confusable names | Names that differ from popular ones only by case, separators, look-alike characters or word order are accepted; internal and public names are not separated, so a public package can take the place of a private one (see [36](../dimensions/36-supply-chain-and-artifact-integrity.md) ("Dependency confusion")) |
| **Archive contents versus metadata** | The manifest, displayed metadata, readme, declared dependencies or source link differ from what is inside the archive or from what install tools read; the registry and the clients parse uploads differently; uploads are not checked for paths and sizes (see [facets](../facets.md) "What is shown versus what is used") |
| Deletion, yanking and republishing | A deleted or yanked version can be published again with different content under the same version; clients and mirrors keep resolving a removed version, or builds break when a depended-on version disappears |
| **Mirrors and caching proxies** | A proxy that merges several upstreams picks the wrong source for a name; cached content is not tied to its checksum, so changed or poisoned upstream content is served; cache keys leave out the upstream or the scope (see [4.6](4.6-caching-and-storage.md) ("Cache keys and isolation")) |
| Access to private packages | Read access to private packages, scopes or repositories is checked in the web interface but not on every download, search, metadata or index endpoint; anonymous or default accounts can read or publish |
| Integrity and provenance | Checksums, signatures and provenance statements are optional, are not checked against the artifact actually served, or can be replaced after publishing; the index and the files are not protected together (see [36](../dimensions/36-supply-chain-and-artifact-integrity.md)) |
