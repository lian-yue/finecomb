# 4.52 Industrial control and cyber-physical safety

Applies to: code and configuration that monitor or control physical processes: PLC programs, SCADA and HMI software, gateways for industrial protocols, robots, building automation, vehicles and in-vehicle networks, medical devices, energy and utility systems. Apply your own knowledge of the specific protocols, controllers and safety standards to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Protocols without authentication** | Control or in-vehicle protocols that have no authentication or integrity by design can be reached from networks that are not trusted; gateways between business and control networks pass any command or address; a secure variant of the protocol exists but is not used |
| **Commands that act on the physical world** | Commands that start, stop, move, change setpoints or load new logic are not authorized and confirmed in proportion to their effect; values are checked only for data type, not against physical limits |
| **Safety functions and interlocks** | Safety interlocks, limits and emergency stops can be disabled, bypassed or overridden by control software, remote commands or configuration changes; safety logic is not kept apart from ordinary control logic |
| **Safe state on failure** | Loss of communication, invalid input, watchdog expiry or a crash does not lead to a defined safe state, or the chosen safe state is wrong for the process (safe is not always "off") |
| Timing and determinism | Control loops miss deadlines under load; blocking calls, memory management or logging delay actions that safety depends on (see [4.36](4.36-embedded-firmware-and-real-time-constraints.md) ("Timing")) |
| Engineering access and updates | Engineering stations, programming ports and remote maintenance accounts are not authenticated or not limited; logic and firmware downloads are not signed or not logged; default credentials remain |
| Operator view | The operator display does not show the real process state; stale or forged values are not marked; alarms can be silenced without a trace (see [facets](../facets.md) "What is shown versus what is used") |
| Security changes and the safety case | A security change (patch, filter, lockout, timeout) is made without checking its effect on safety functions and response times |
