# 4.76 Health data and medical interoperability

Applies to: electronic health record (EHR) systems, health data APIs and exchange formats, interface engines, medical imaging systems and viewers, patient portals and apps. Apply your own knowledge of the specific health data standards and platforms to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Access scopes and consent on every API** | Scopes, patient context and consent are checked in the main app but not in every API, search, bulk export or subscription; a token for one patient reaches others by changing an ID or search parameter; staff access is not limited to patients they care for (see [28](../dimensions/28-authorization-and-access-control.md) ("Horizontal privilege escalation")) |
| **Parsing exchange and imaging formats** | Health messages, documents and imaging files from other systems are parsed without limits; their fields carry markup or scripts that viewers render; an imaging file that is also a valid file of another type is accepted (see [4.3](4.3-decoding-untrusted-external-data.md) ("Format confusion")) |
| **Interfaces between systems** | Interface engines, message listeners and imaging nodes accept messages and queries from anyone on the network, without authentication or encryption, and trust sender identifiers that the sender sets itself (see [facets](../facets.md) "Authenticity of identities and addresses") |
| Audit of every access | Reads, searches, exports, prints and API calls on records are not all logged with the real user and patient; the people being logged can change the logs; nobody reviews them (see [4.23](4.23-security-audit-logs.md) ("Event scope")) |
| De-identification that can be reversed | Identifiers remain in free text, image pixels, file metadata, dates, rare values or combinations of fields; pseudonyms can be recomputed from the identifiers (see [30](../dimensions/30-privacy-data-governance-and-compliance.md) ("Anonymization")) |
| Emergency access | Emergency access has no stated reason, time limit or later review; more people have it than need it; it becomes the normal way in |
| **Sharing with apps and third parties** | Apps get wider scopes, longer-lived tokens or more data than the patient approved; apps are not registered or reviewed; revoking consent does not stop access (see [30](../dimensions/30-privacy-data-governance-and-compliance.md) ("Third-party sharing")) |
| Patient matching | Records are matched or merged on weak or partial identifiers, so data lands in the wrong patient's record or is shown to the wrong person; a wrong merge cannot be undone |
