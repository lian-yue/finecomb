# 4.70 Code hosting and version control

Applies to: version control clients and servers, code hosting platforms, code review tools and the integrations that run on repository events. Apply your own knowledge of the specific version control system and hosting platform to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Content that runs on clone or checkout** | Hooks, configuration, filters, submodule settings, large file storage settings or attributes that come from the repository run commands or reach arbitrary URLs when a person or a server clones, fetches or checks out (see [4.22](4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md)) |
| **Names on special file systems** | Ref, path and file names that collide on case-insensitive or normalizing file systems, use reserved or alternate names, or contain unusual characters let a checkout write into the repository's own metadata directory or outside the working tree (see [4.8](4.8-file-systems-and-paths.md) ("Path length and characters")) |
| Import and mirroring | Repository import, mirroring, submodule fetches and webhooks fetch URLs a user supplies, including internal addresses, local paths and other protocols (see [4.21](4.21-outbound-requests-and-server-side-request-forgery.md)) |
| **Forks, pull requests and CI from forks** | Forks keep access to private content or secrets; code from a fork's pull request runs with the base repository's secrets or write access; approvals and status checks for one commit still count after new commits are pushed (see [4.33](4.33-build-scripts-ci-and-infrastructure-as-code.md) ("Privileged triggers")) |
| **Protected branches and required reviews** | Protection rules can be bypassed through another path (API, merge queue, force push, tag or branch rename, admin override, bots with broad tokens); authors can approve their own changes through a second account, or change code after approval |
| Access through every repository feature | Access to a private repository is enforced in the web view but not in the version control protocol, archives, raw file links, search, API tokens, deploy keys, or references from issues and pull requests in other repositories (see [28](../dimensions/28-authorization-and-access-control.md) ("Consistency across entry points")) |
| Secrets in history | Secrets removed from the latest version remain in history, forks, pull request refs, caches or archives; secret scanning covers only some of these |
| Large or deep repositories | Very large, deep or highly compressed repositories, huge diffs, long lines or many refs exhaust memory, CPU or disk in servers, review tools and clients (see [20](../dimensions/20-resource-bounds-and-backpressure.md)) |
