# 4.64 End-to-end encrypted messaging

Applies to: messaging apps, libraries and servers that offer end-to-end encryption, including one-to-one and group protocols, multi-device support and encrypted backups. Apply your own knowledge of the specific messaging protocol and its implementations to each row.

| Checkpoint | What counts as a problem |
| --- | --- |
| **Identity keys and verification** | A change of a contact's identity key or device list is accepted silently, or with a warning that is easy to miss; users cannot verify keys, or verification is not bound to the keys actually used; the client trusts the server's key directory with no transparency or consistency check |
| **Adding and linking devices** | Whoever controls the server, the account recovery or the phone number can add a device without approval from an existing device and without a visible notice; the linking step can be relayed to an attacker's device; history sent to a new device is not protected |
| **Group membership and keys** | The server or a member without the right can add members or devices without a change that authorized members signed and everyone sees; removed members keep receiving new messages because group keys are not updated; one member can send messages that appear to come from another (see [4.54](4.54-sync-collaboration-and-offline-clients.md) ("Removing members")) |
| Forward secrecy and recovery | Old message keys or long-term keys are kept longer than needed, so a device compromise exposes past messages; sessions do not recover after a compromise because keys are not refreshed; session state is reused after a restore or on a cloned device (see [4.4](4.4-cryptography-and-credentials.md) ("Protocol state and replay")) |
| Metadata visible to the server | Who talks to whom and when, group membership, contact lists and message sizes are visible to the server or stored beyond what the design promises; push notifications carry message text or sender names through a third-party push service |
| **Backups and their keys** | Message backups or cloud copies are unencrypted, or encrypted with a key the provider holds or with a weak user secret that can be guessed offline, so the backup quietly undoes end-to-end encryption |
| Abuse reporting | Reporting sends more than the messages the user chose to report; reported messages cannot be tied to their real sender, or can be forged; moderation hooks let the server read messages without a user action |
| Attachments and previews | Attachments are fetched from storage outside the encrypted channel without checking them against the key and hash in the message; link previews leak the link or the user's address to the server or to the linked site; media is parsed before the user opens it (see [4.3](4.3-decoding-untrusted-external-data.md)) |
