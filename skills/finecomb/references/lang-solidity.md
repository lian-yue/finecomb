# A.13 Solidity and Vyper (EVM)

| Checkpoint | What counts as a problem |
| --- | --- |
| **Reentrancy** | External calls (including transfers and token callbacks, such as ERC777 hooks, ERC721's `onERC721Received` and ERC1155's receive callbacks) happen before state updates; cross-function and cross-contract reentrancy; read-only reentrancy: during a callback, another contract reads a view function (such as a price) that has not been updated yet; the code is not ordered as "checks-effects-interactions", and there is no reentrancy lock |
| **Delegate calls** | `delegatecall` runs in the caller's storage context: when the target address is controllable, it can overwrite any slot; storage layout collisions between the proxy and the implementation contract; function selector clashes in transparent proxies |
| **Unprotected initialization** | The `initialize` of an upgradeable contract has no guard against being initialized again, or the implementation contract itself was never initialized, so someone else can initialize it first, become the owner, and even make the implementation contract self-destruct (on chains that have not implemented EIP-6780) |
| **Callback origin** | Whether flash loan, swap and mint callbacks (such as `uniswapV3SwapCallback` and `onFlashLoan`) check that the caller is the expected pool or lender, and confirm that this callback comes from a call this contract started itself; otherwise anyone can call the callback directly and make the contract pay or record entries based on forged parameters |
| **Meta-transaction sender** | A contract that supports ERC-2771 takes the real sender from the end of the call data, and may only do this for a trusted forwarder; when the contract also offers a `multicall` that calls itself with `delegatecall`, an attacker can append any address to the end of each sub-call and impersonate anyone |
| Transient storage | EIP-1153 transient storage lasts for the whole transaction, not only for the current call: later calls in the same transaction read the leftover values, so when it is used for locks or temporary parameters, whether it is cleared before returning; `TSTORE` costs only 100 gas, so the 2300 gas of `transfer` and `send` can no longer stop the recipient from changing state |
| Phantom functions | Calling a function on a contract that does not implement it but has a fallback does not revert (such as calling `permit` on WETH); the `transferFrom` that follows then directly spends the allowance the user gave earlier |
| Balances and internal accounting | Using `balanceOf(address(this))` or `address(this).balance` as the ledger; an attacker can transfer tokens in directly or force-send ETH (through self-destruct, or by sending to a precomputed address in advance) to change the result |
| Sending and receiving ETH | Missing `receive` or `fallback`, so refunds cannot be received; when pushing ETH to users, a recipient that reverts blocks the whole flow; `msg.value` left unused in a `payable` function stays in the contract |
| Account checks | Using `tx.origin` for permission checks; using `extcodesize` or `code.length` to decide whether the other side is an externally owned account (it is 0 while a constructor runs; after EIP-7702, externally owned accounts can also have code) |
| Low-level calls | The return values of `call`, `delegatecall` and `send` are not checked; a call to an address with no code also returns success; the other side returns huge data, and copying it runs out of gas (return data bomb) |
| Integers | Before Solidity 0.8, overflow is not checked by default; arithmetic inside `unchecked` blocks; truncation in type conversions (such as `uint256` to `uint128`); conversions between signed and unsigned |
| **Precision and rounding** | Dividing before multiplying loses precision; which side the rounding direction favors; conversion between tokens with different decimals |
| Hash collisions | Hashing the output of `abi.encodePacked` over several dynamic types collides (`("a","bc")` and `("ab","c")` give the same result) |
| Signatures | `ecrecover` returns the zero address for an invalid signature; signatures are malleable (high s values); a signature lacks a nonce, chain ID or deadline; an audited signature library should be used |
| `msg.value` reuse | Using the same `msg.value` more than once in a loop or a batch call (multicall) |
| Randomness | Using the block timestamp, block hash or `prevrandao` as a randomness source; block producers or contracts in the same block can predict or influence the result |
| Time and blocks | Relying on the exact value of `block.timestamp`; on layer-2 networks, `block.number` and `block.timestamp` mean something different from mainnet |
| **Denial of service** | Unbounded loops; when transferring to a list of addresses one by one, one recipient that reverts makes all of them fail (let users withdraw themselves instead); the flow can only continue if some external call succeeds |
| Gas forwarding | An external call forwards at most 63/64 of the remaining gas: a caller can deliberately supply too little gas, so the inner call fails for lack of gas while the outer call keeps running, and code that does not check the return value or swallows the failure with `try/catch` treats this as a normal branch; the fixed 2300 gas of `transfer` and `send` may not be enough after opcode repricing (such as EIP-1884 raising the cost of `SLOAD`), and the call fails when the recipient is a contract wallet |
| Self-destruct and code replacement | After EIP-6780, `selfdestruct` deletes code and storage only when it runs in the same transaction that created the contract; in every other case it only moves the balance, and logic that relies on the old semantics breaks; for contracts created and destroyed in the same transaction, and on chains that have not implemented EIP-6780, `CREATE2` combined with self-destruct can still redeploy different code at the same address |
| Visibility and inheritance | Wrong function visibility; linearization order and overrides under multiple inheritance; state variable shadowing |
| Storage and data location | Mixing `storage` and `memory` references, so the object that gets changed is not the intended one; data left behind after `delete` on a mapping or a struct; uninitialized storage pointers in old versions |
| Token interfaces | Assuming every ERC20 returns `bool` (some major tokens do not); the race when `approve` changes an allowance; not using a safe wrapper |
| `permit` and off-chain approvals | A permit signature can be submitted first by someone else, making the original transaction revert (a permit that has already taken effect should be tolerated); permits signed through phishing |
| Structured signature encoding | Whether the EIP-712 type string matches the struct fields (names, order, and nested struct types appended after it, sorted by name); encoding of dynamic types and arrays; whether the domain separator includes the chain ID and the contract address, and whether it is recomputed with the current chain ID after a chain fork |
| Permit2 and signature approvals | A user's approval to Permit2 lets a single signature move all approved tokens; when a contract submits a Permit2 signature on behalf of a user, whether the recipient, amount, deadline and nonce in the signature are all checked, and whether the extra data (witness) is bound to the content of this operation |
| Events | Key state changes emit no events; event parameters do not match the actual state |
| **Compiler** | `pragma` does not pin a version; using a compiler version with known bugs (such as the reentrancy lock bug in Vyper 0.2.15, 0.2.16 and 0.3.0, which led to the theft from several Curve pools in 2023); optimizer-related bugs; the EVM version the code is compiled for produces opcodes (such as `PUSH0`) that the target chain does not support |
| Inline assembly | Assembly bypasses type and bounds checks; management of memory pointers and the free memory pointer |
| Constants and immutables | Constructor arguments and immutables cannot be changed once written wrong; a hard-coded address points to a different contract on another chain |
