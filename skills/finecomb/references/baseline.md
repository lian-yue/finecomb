# Part I: Establish the factual baseline

1. **Set the scope and its basis**: First read the applicable rules, then the overview documents, flow contracts and test matrix relevant to this review. Per [invocation and scope resolution](scope.md#invocation-and-scope-resolution), list the target, the exclusions and the suspected items, plus the review time, a verifiable identity of the source or artifacts, the actual configuration, the platform and the build conditions. Judge missing documents that the project requires per [43](dimensions.md#43-documentation-consistency).
2. **Build the language and build inventory**:
   - Identify the language of each path by extension, file header and build manifest. Also find languages embedded in strings or configuration (SQL, regular expressions, Shell, templates, HTML, expressions).
   - List the build systems and manifest files (such as `go.mod`, `package.json`, `pyproject.toml`, `requirements*.txt`, `Cargo.toml`, `CMakeLists.txt`, `Makefile`, `pom.xml`, `build.gradle`, `*.csproj`, `composer.json`, `Gemfile`), and the declared language and runtime versions.
   - Find the entry forms of each language: executable entry points, command-line scripts, package exports, route registration, plugin registration, code run at import time.
   - Find cross-language boundaries (see [4.32](specialties.md#432-cross-language-boundaries-and-native-extensions)).
   - For each language, pick the matching table in [Appendix A](languages.md).
3. **Build the object inventory**: Read the implementation per [scaling to the request](scope.md#scaling-to-the-request). List file responsibilities, public entry points, externally reachable routes and admin entry points, background flows and automatic behaviors (threads, coroutines, timers, finalizers, code run at import or load, signal handlers), shared state, invariants and side effects. For dynamic registration, reflection, plugins and conditional compilation, reachability cannot be judged by counting text references alone. Handle content that is not hand-written per the project's maintenance boundaries.
4. **Confirm upstream and downstream**: List the dependencies, callers, persisted data and external systems actually used. Distinguish "present in source", "included in the build", "enabled in deployment" and "reachable from outside". Without deployment evidence, keep the condition attached; do not treat the default configuration as a production fact.
5. **Determine the target type**: For security-related targets, set the assets, attacker capabilities and trust boundaries per [the next section](#threat-model-and-attack-chains), then pick [specialties](specialties.md) per [mapping known attack mechanisms](#mapping-known-attack-mechanisms).
6. **Check existing evidence and choose only the execution you need**: First check whether reusable records are still valid. Choose actions that need execution per [execution boundaries during review](scope.md#execution-boundaries-during-review) and the project's test strategy; [Part VII](tools.md) is only for picking tools. Issues that a read-only review can settle statically may be reported directly. For candidate issues that need reproduction, choose only an authorized smallest entry point.

## Threat model and attack chains

For security-related targets, record the facts below. Write missing information as assumptions or unverified items. Do not invent preconditions to close an attack chain.

| Subject | What to confirm |
| --- | --- |
| Assets and security goals | Data, credentials, permissions, funds, compute resources and service availability; who owns them, and which reads, changes and interruptions must not happen |
| Attacker capabilities | What each of these can do: anonymous users, ordinary users, other tenants, low-privilege operators, a compromised client or dependency, **other users or low-privilege processes on the same machine**, **web pages in a local browser** (which can send requests via localhost and DNS rebinding), external contributors whose commits trigger CI, upstream dependency or plugin authors; whether credentials, network position and user interaction are preconditions |
| Controllable inputs | Requests, messages, files, stored records, configuration, environment, build inputs, source code or rules handed to an interpreter; which fields can be controlled directly and which can only be influenced indirectly |
| Trust boundaries | Browser to service, between tenants, service to data layer, build to release, data to interpreter, script to host, local low-privilege process to high-privilege service, one language to another; at each crossing, who verifies identity, content and permissions |
| Attack surface and blocking points | The entry points actually enabled and the controls at each layer; whether proxies, gateways, permission checks, sandboxes and isolation policies can be bypassed, and whether the configuration they rely on has been verified |
| Final impact | The full path from controlled input to a violated security goal, the number of attempts and the cost needed, the scope of impact, persistence and recovery conditions |

Trace along "input source → decoding and normalization → validation and authorization → sensitive operation → state or external result". Focus on whether the object that was validated is the same object that is finally used, and whether data is still protected after it passes through storage, queues, callbacks or a second parse. A valid signature only shows that the signed content passed verification. It does not mean the content follows business rules or that the caller is allowed to perform the action.

Several candidate issues can form an attack chain, but every step needs evidence that it is reachable. If the chain relies on an administrator's active cooperation, a key not proven to be obtainable, or a deployment configuration that does not exist, do not report it as directly exploitable by an ordinary user. For source code review, the data flow and threat analysis methods of [OWASP Secure Code Review](https://cheatsheetseries.owasp.org/cheatsheets/Secure_Code_Review_Cheat_Sheet.html) can serve as a reference.

When a mapping to an external standard is needed, record the version, the items and the reason for applicability actually used. For example, [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) uses versioned item identifiers. Completing this checklist does not mean certification against any standard.

## Mapping known attack mechanisms

This table maps features of an entry point to where to check. It does not repeat the criteria, and it does not require reporting the same issue again.

| If the target has | How it has been broken before | Go to |
| --- | --- | --- |
| Connects to an address taken from external data (parameters, stored records, configuration, redirects, webhooks, callback URLs) | Outbound requests hit the internal network / cloud metadata / the file protocol; DNS rebinding bypasses allowlists | [4.21](specialties.md#421-outbound-requests-and-server-side-request-forgery) |
| Starts subprocesses or interpreters, uses eval, deserializes bytes into object graphs, loads plugins | Code runs even without "splicing into a command": inherited environment variables, gadgets, decoders that read local files or reach the network | [4.22](specialties.md#422-subprocesses-dynamic-execution-and-decoder-side-effects) |
| A parser fetches external entities or references | Reads local files, makes outbound requests | [4.3](specialties.md#43-decoding-untrusted-external-data) |
| Cookies / session credentials are sent automatically with browser requests, and the entry point changes state | The user is tricked into sending the request from another site | [4.14](specialties.md#414-server-request-handling-and-middleware), [4.18](specialties.md#418-user-interfaces-and-accessibility) |
| Writes external input into a redirect target (`Location`, return after login, generic redirects) | Sends people to a phishing page, or sends tokens somewhere else | [4.18](specialties.md#418-user-interfaces-and-accessibility), [4.5](specialties.md#45-authentication-sessions-and-tokens) |
| Parses HTTP itself, or sits between two HTTP implementations (a proxy, a CDN in front) | Disagreement on length and chunked semantics makes the front and back see different requests; unvalidated headers end up in cache keys | [4.14](specialties.md#414-server-request-handling-and-middleware), [4.2](specialties.md#42-protocols-and-frame-parsing) |
| Uses untrusted strings as hash table / dictionary keys | Collisions let a single request max out the CPU | [20](dimensions.md#20-resource-bounds-and-backpressure), [27](dimensions.md#27-security-and-trust-boundaries) |
| Internal package names also resolve on public registries | Someone registers the same name publicly, and the build pulls the fake package | [36](dimensions.md#36-supply-chain-and-artifact-integrity) |
| Logs / metrics / tracing interpret lookups or expressions inside messages | Log content turns into outbound requests or code execution | [4.13](specialties.md#413-logs-metrics-and-tracing), [4.22](specialties.md#422-subprocesses-dynamic-execution-and-decoder-side-effects) |
| Binds request objects directly to internal models, or recursively merges external objects | Writes unauthorized fields, or affects other objects through prototype pollution | [28](dimensions.md#28-authorization-and-access-control), [4.3](specialties.md#43-decoding-untrusted-external-data) |
| Updates business state after receiving an external callback | A valid signature is reused across tenants or operations, or old events take effect again and again | [4.24](specialties.md#424-webhooks-and-external-events) |
| Writes shared data based on a lease or a leader election result | The old holder recovers and keeps writing, overwriting the new holder's results | [4.25](specialties.md#425-distributed-coordination-and-leases) |
| An LLM reads external content and then calls tools | The external content rewrites the task, then uses the tools' permissions to read or modify resources it should not touch | [4.26](specialties.md#426-llms-and-tool-calling) |
| Runs source code, expressions, templates, queries or rules supplied from outside | A script gets a host object and escapes the sandbox; built-in functions bypass metering, and one line of code exhausts memory or CPU | [4.27](specialties.md#427-interpreters-compilers-and-virtual-machines), [20](dimensions.md#20-resource-bounds-and-backpressure) |
| Forwards other people's traffic, or takes over system routing or name resolution | Its own traffic is captured by itself and forms a loop; name resolution or IPv6 bypasses the tunnel and leaks; it is used as an open proxy or a reflection amplifier | [4.28](specialties.md#428-tunnels-proxies-and-the-network-data-plane) |
| Allows, blocks, routes or rate-limits by a rule table | Suffix or wildcard boundaries are wrong; a rule is shadowed by an earlier rule; no normalization before matching | [4.29](specialties.md#429-rule-and-policy-matching) |
| Calls system interfaces directly, or holds raw descriptors or handles | After a descriptor number is reused, someone else's descriptor is closed by mistake; a call interrupted by a signal is treated as a failure; lengths returned by the kernel are not validated | [4.30](specialties.md#430-os-interfaces-system-calls-and-descriptors) |
| Generates code from a schema, IDL or template | Names in the schema are injected into the generated code; old artifacts remain after their input is deleted | [4.31](specialties.md#431-code-generators-and-build-time-tools) |
| Two languages call each other, share memory or share data definitions | Integer widths and null values do not match; exceptions cross a boundary that does not support them; the two sides disagree on who owns memory | [4.32](specialties.md#432-cross-language-boundaries-and-native-extensions) |
| CI splices event fields into scripts, or runs external commits in a privileged context | External contributors get release credentials or write access | [4.33](specialties.md#433-build-scripts-ci-and-infrastructure-as-code), [36](dimensions.md#36-supply-chain-and-artifact-integrity) |
| Publishes packages for others to install or link | Published content carries secrets; code runs at install time; breaking changes are not reflected in the version number | [4.34](specialties.md#434-publishable-libraries-sdks-and-packages) |
| The client auto-updates, or can be launched by other apps or web pages | Update packages are replaced or downgraded; exported components or custom protocols are invoked by other apps or web pages | [4.35](specialties.md#435-client-apps-extensions-and-auto-update) |
| A high-privilege resident service opens a control port on the local machine | A local low-privilege process or a web page in a browser drives it to perform privileged operations | [4.35](specialties.md#435-client-apps-extensions-and-auto-update), [28](dimensions.md#28-authorization-and-access-control), [34](dimensions.md#34-runtime-environment-and-deployment-contract) |
| Runs in firmware, drivers or interrupt context | Interrupt reentry corrupts shared data; power loss while writing flash bricks the device; the device cannot boot after an interrupted update | [4.36](specialties.md#436-embedded-firmware-and-real-time-constraints) |
| Reruns batch jobs, trains models or loads model files | Reruns write duplicates; training and test data leak into each other; loading a model file runs code | [4.37](specialties.md#437-data-processing-batch-jobs-and-machine-learning), [4.22](specialties.md#422-subprocesses-dynamic-execution-and-decoder-side-effects) |
| On-chain contracts hold or transfer assets | Reentrancy, price manipulation, front-running, storage layout conflicts after an upgrade | [4.38](specialties.md#438-smart-contracts-and-on-chain-interaction) |
| Runs resident for a long time, unattended | Hot loops while idle; counter wraparound; certificates expire while running; state goes stale after sleep and wake | [45](dimensions.md#45-long-running-and-resident-processes) |
