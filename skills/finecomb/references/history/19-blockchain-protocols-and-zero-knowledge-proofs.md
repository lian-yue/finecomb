# 19 Blockchain protocols and zero-knowledge proofs

| Pattern | Historical cases | What to look for | Where it lands |
| --- | --- | --- | --- |
| **Values assigned in a circuit but not constrained** | Zcash Orchard (CVE-2026-54496, disclosed in 2026: the base point of a scalar multiplication was written with `assign_advice` but had no copy constraint, so a malicious prover could swap the base point and compute any number of valid nullifiers for the same note, forging unlimited ZEC; it went unnoticed for four years); Tornado Cash (2019, the MiMC circuit used `=` instead of `<==`, so a Merkle root could be forged to withdraw deposits) | Whether every witness value is bound by constraints to its real source; whether tests use only honest provers | [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md) ("Under-constrained circuits", "Malicious-prover tests"), [Zero-knowledge circuits](../lang-zk.md), [8](../dimensions/8-functional-correctness-and-fitness-for-requirements.md) ("Completeness of verification") |
| **Missing items in the non-interactive challenge** | Frozen Heart (2022, the Fiat–Shamir challenges in several PlonK, Bulletproofs and Girault proof implementations did not include all public inputs, so proofs could be forged) | Which items the hash for the challenge value includes | [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md) ("Challenges and transcripts"), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Custom schemes and proof structure") |
| **Flaws in parameter generation** | Zcash (CVE-2019-7167, extra elements in the parameters of the original scheme let a cheating prover turn a proof of one statement into a proof of another, allowing unlimited forgery) | How trusted setup parameters are generated and verified, and which version they belong to | [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md) ("Trusted setup and parameters") |
| **Curve subgroups give one secret several valid identifiers** | Monero and other CryptoNote coins (2017, key images were not checked to lie in the prime-order subgroup; the cofactor of 8 let the same funds produce several valid key images, allowing unlimited double spending) | Subgroup checks on curve points; whether identifiers that "can be used only once" are unique | [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Completeness of verification", "Uniqueness and single use"), [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md) ("Deriving unique identifiers") |
| **An optimized path skipped the double-spend check** | Bitcoin (CVE-2018-17144, for performance, block validation skipped the check for duplicate inputs within a transaction, which could both crash nodes and allow double spending) | Whether the fast path leaves out checks that the slow path does | [31](../dimensions/31-performance-memory-and-latency.md) ("Optimized paths that skip validation"), [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) |
| **Adding amounts overflows and creates coins from nothing** | Bitcoin (CVE-2010-5139, adding two huge outputs overflowed into a negative number, bypassed validation, and produced about 184 billion BTC) | Range and overflow checks before amounts are summed and compared | [14](../dimensions/14-boundaries-numbers-and-text.md), [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Conservation of totals"), [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) |
| **Ambiguous keys in the verification cache** | Liquid Network (2026, the cache key for range proof verification results was built by directly concatenating variable-length fields, so another transaction hit the same cache entry and skipped verification, minting about 4000 L-BTC from nothing; five days after the fix commit was public, it was still not deployed) | Whether the fields of a cache key have length prefixes; the window between a fix going public and being deployed | [4.6](../specialties/4.6-caching-and-storage.md) ("Cache keys and isolation"), [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) ("Verification result caches") |
| Forgery that cannot be detected from outside | Before the privacy coin bugs above were fixed, there was no cryptographic way to confirm whether they had been exploited; Zcash limits losses by counting inflows and outflows per pool (turnstile) | Whether systems that hide details have independent supply accounting and monitoring | [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) ("Supply accounting for shielded pools"), [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Conservation of totals") |
