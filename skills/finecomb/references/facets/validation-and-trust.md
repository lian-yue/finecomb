# Validation and trust

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Completeness of verification** | Does this verification (validator, constraint, signature or proof verification, authorization rule, type check) accept only what it should? Ask the reverse: what other inputs can also pass? Does a pattern match have to cover the whole string, or does finding one piece count as passing? When the sender marks an extension or parameter as "must understand" and the receiver does not recognize it, does the receiver reject it or ignore it? | Tests only feed correct input, and correct input passing does not mean bad input is rejected; reviews only look at "whether the checks that were written are right", not "which check is missing" | One missing constraint in the Zcash Orchard circuit allowed unlimited coin forgery; "goto fail" skipped signature verification; checking only that a SAML signature exists without verifying it | [8](../dimensions/8-functional-correctness-and-fitness-for-requirements.md) ("Completeness of verification"), [27](../dimensions/27-security-and-trust-boundaries.md) ("Whether regex allowlists match the whole string"), [4.2](../specialties/4.2-protocols-and-frame-parsing.md) ("Unknown must-understand items"), [28](../dimensions/28-authorization-and-access-control.md), [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Batched and aggregated verification") |
| **Whether declared controls actually take effect** | Are the security controls written in annotations, decorators, route tables and configuration really attached to every entry point that needs them? Can inheritance, generics, interfaces, route order or request methods make the framework silently not apply them? Can setting another option, or setting options in another order, silently reset it? Is it built into release builds, or only into debug builds? | Once it is "written" in the code, it is treated as "in place"; a later setting or a build mode quietly turns it off | Spring Security annotations on a generic parent class were not resolved; access control was configured only for GET and POST, so another method goes straight in | [28](../dimensions/28-authorization-and-access-control.md) ("Where checks happen", "Whether declared controls take effect"), [4.14](../specialties/4.14-server-request-handling-and-middleware.md) ("Request methods"), [32](../dimensions/32-configuration-and-defaults.md) ("Options that reset each other"), [16](../dimensions/16-language-and-runtime-pitfalls.md) ("Assertions and build modes") |
| **What a check covers** | Which bytes, files, fields and paths do the signature, integrity check, scan or sanitizer actually cover? Does anything that is loaded, executed or used at run time fall outside that coverage? | The check "passed", and no one asks whether it checked everything | APK signatures do not cover the bytes at the start of the file; data can be appended to the Authenticode signature area; Electron's integrity check does not cover the V8 snapshot | [36](../dimensions/36-supply-chain-and-artifact-integrity.md) ("What a signature covers"), [24](../dimensions/24-encoding-and-persistent-formats.md) ("Integrity checks") |
| **Missing values and defaults** | Where does it land when something is missing: when the authentication header, identity, tenant, a field, metadata or an optional component in front (proxy, gateway, plugin) is absent, do the default value and the default branch deny or allow? Does the default value itself carry privilege? | Test environments are always fully configured; the zero or empty value happens to mean admin or "everything" | Requests without an authentication header ran as root (OMIGOD); failing to get the caller's identity was treated as uid 0 (polkit); AS2 validation was skipped when no DMZ proxy was deployed (CrushFTP) | [28](../dimensions/28-authorization-and-access-control.md) ("Defaults when identity is missing"), [29](../dimensions/29-fail-safe-behavior-and-dangerous-operations.md) ("Failure direction"), [32](../dimensions/32-configuration-and-defaults.md) |
| **Where trust comes from** | Who supplied this value: the peer, a request header, upstream, configuration, environment variables, a local process, a low-privilege user, another tenant, a dependency's default behavior? Are values that seem to come from infrastructure but are actually controlled indirectly by the other side (host names from reverse lookups, fields in the peer's certificate, upstream responses, DNS records) treated as trusted? On what grounds are they trusted? | "From inside", "from the local machine" and "from configuration" are trusted by default | Local requests treated as authenticated; Next.js skipping middleware based on an internal request header; configuration injection in IngressNightmare; the nginx mail proxy putting a host name from a reverse lookup into the authentication request without validation | [27](../dimensions/27-security-and-trust-boundaries.md) ("Classifying input sources"), [4.14](../specialties/4.14-server-request-handling-and-middleware.md) ("Proxy trust") |
| **Privileged code handling low-privilege input** | Is high-privilege code (setuid programs, the kernel, drivers, privileged services, admin consoles, build machines) handling things that a low-privilege party can control: environment variables, files, paths, configuration, root directories, device requests? What can data that a low-privilege party can change (owner references, finalizers, labels, status fields, referenced names) make automation running with high privileges (controllers, garbage collection, schedulers, scheduled jobs, workflows) do on its behalf? On each entry from a less privileged mode, are the CPU registers and mode bits that privileged code relies on reset to trusted values, or kept from the less privileged side? | Authors of high-privilege code write it with the habits of ordinary programs; the privileges of automation are not counted as the requester's | glibc parsing environment variables in setuid programs; sudo loading configuration from a user-specified root directory; a privileged service led to a system file through a link in a user-writable directory | [4.47](../specialties/4.47-local-privileged-components-and-local-privilege-escalation.md), [4.48](../specialties/4.48-kernel-drivers-device-emulation-and-virtualization.md) ("Execution state at privilege entry"), [4.22](../specialties/4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md), [28](../dimensions/28-authorization-and-access-control.md) ("Indirect effects of fields") |
| **Binding and context** | In what context was a result (authentication, authorization, signature, proof, cache entry, session) obtained? Can it be carried into another context and still be treated as valid? Does a result obtained in a callback or hook belong to one of the candidate objects, or to the object that finally takes effect? When an authorization, signature or approval points at an object, does it use a stable identity, or a position (index, offset, order, slot)? On another chain, in another layout or after the contents change, can that position point at something else? Is the data a check reads parsed from its actual structure, or read at an assumed offset or position in the structure? When the object's contents can still change after approval (an order, a cart, a document), is the approval bound to those contents, or only to a stable ID? | It was right at the moment of verification; the problem is where it is reused later; when the code was written, positions and objects always matched one to one | nginx TLS sessions reused across virtual hosts, bypassing client certificate verification; an SSO token issued by one tenant accepted by another tenant | [27](../dimensions/27-security-and-trust-boundaries.md) ("Whether binding chains are enforced"), [10](../dimensions/10-apis-and-contracts.md) ("Callbacks versus the final result"), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Binding and context"), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Authorized operations that refer to objects by position"), [Solana](../lang-solana.md) ("Offset fields of signature-verification precompiles"), [4.39](../specialties/4.39-payments-accounting-and-billing.md) ("Paid amount at completion") |
| **Who can loosen a restriction** | Who can set and change restrictions, policies, directives and permissions? Can a source less trusted than the level above it (a subresource's response, a derived identity or credential, a plugin or extension, the output of a model or automation, an option carried by a single request, a lower configuration layer) loosen a restriction set above it, rather than only tighten it? Can a derived identity, session, token or subtask end up with more permission than the party it was derived from? When several policies are merged, is a conflict resolved to the stricter value, or to the later or looser one? When several conditional grants apply, is each request covered by one whole grant, or are their conditions and field sets merged separately? | The way to loosen a restriction looks like just another option; nobody compares a derived object's permissions with its source | A policy in a subresource's response header loosening the referrer policy of the whole page; temporary credentials with a session policy checked only for explicit denies on another check path; an agent deciding where it may write from a working directory given by the model | [28](../dimensions/28-authorization-and-access-control.md) ("Permission ceiling of derived identities"), [27](../dimensions/27-security-and-trust-boundaries.md) ("Narrowing across multi-step chains"), [32](../dimensions/32-configuration-and-defaults.md) ("Merge semantics"), [4.18](../specialties/4.18-user-interfaces-and-accessibility.md) ("Scope of directives set by responses"), [4.26](../specialties/4.26-llms-and-tool-calling.md) ("Rewriting its own constraints"), [28](../dimensions/28-authorization-and-access-control.md) ("Combining conditional grants") |
| **Authority beyond the job** | Does each credential, identity, token, service account, database user, container, process and agent tool hold only the permissions its job needs? If it is misled, injected into or stolen, what else can it read, write, call or deploy? Are the permissions needed at run time kept apart from those needed for installation, migration and release? Can one compromised component spread further because credentials are shared, or because downstream services trust it without conditions? | Permissions are granted until things run; nobody narrows them by asking how much damage they allow when something goes wrong | An over-privileged token in CI letting an outsider commit to the repository, and the change shipping in an official release; internal services behind network isolation skipping authentication because "nobody outside can reach them" | [4.33](../specialties/4.33-build-scripts-ci-and-infrastructure-as-code.md) ("Token permissions"), [28](../dimensions/28-authorization-and-access-control.md) ("Granularity"), [27](../dimensions/27-security-and-trust-boundaries.md) ("Reach of granted permissions"), [4.26](../specialties/4.26-llms-and-tool-calling.md) ("Credentials held by agents"), [Targets that are not source code: Kubernetes clusters](../targets/kubernetes-clusters.md) |
| **What a limit is bound to** | What object are counts, quotas, rates and failure counters attached to: the account or the resource, or a session, connection, source address or temporary identifier that the attacker can swap or reset at any time? Can the attacker split one action into several lines or entries that are each counted alone? Where is the counter, lockout or quota kept, and can the limited party make it disappear: push it out of a bounded cache with other keys, wait out a short expiry, cause a restart, or reach another replica that keeps its own count? | A limit that "exists" is treated as effective; nobody asks where its state lives | The failure limit for one-time passwords was attached to a temporary session, so recreating sessions allowed brute force in parallel | [4.5](../specialties/4.5-authentication-sessions-and-tokens.md) ("One-time codes", "Brute-force protection"), [20](../dimensions/20-resource-bounds-and-backpressure.md) ("Quota ownership and accounting", "Storage of limit state"), [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Anti-automation"), [4.6](../specialties/4.6-caching-and-storage.md) ("Eviction policy") |
