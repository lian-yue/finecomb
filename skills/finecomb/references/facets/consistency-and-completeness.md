# Consistency and completeness

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Consistency across sibling branches and similar entry points** | Do the sibling branches in the same switch, table or function, and the multiple entry points of the same kind (similar APIs, newly added functions, another request method, another encoding), all do the same set of checks? Does one of them do it while another does not? Do the implementations of the same feature on different platforms or in different languages (for example the Android and iOS sides of one plugin) check the same things? | Each branch looks "reasonable" on its own | glibc iconv checking capacity for only one kind of control sequence; Euler's newly added donate function lacking the health check that all the other functions had; authorization attached only to the detail API | [28](../dimensions/28-authorization-and-access-control.md) ("Consistency across entry points"), [20](../dimensions/20-resource-bounds-and-backpressure.md) ("Limits that cover every branch"), [3](../dimensions/3-duplication.md) ("The same check scattered in many places"), [2.1](../questions.md#21-for-each-public-entry-point) |
| **Shortcuts and fast paths** | Do fast paths, caches, batch processing and defaults added for performance or convenience skip the checks on the slow path? Can the exceptions that skip checks (particular identities, values, object states, markers) be created, claimed or kept up for a long time by the party being checked? | Tests of the fast path only check whether the result is right; exception conditions are assumed to be met only by the system itself | Bitcoin skipping the duplicate input check to speed things up; authentication results cached and then reused across contexts | [31](../dimensions/31-performance-memory-and-latency.md) ("Optimized paths that skip validation"), [28](../dimensions/28-authorization-and-access-control.md) ("Whether the restricted side can create or claim an exemption") |
| **Combinations of configuration and features** | Does the defect appear only when certain configuration options, modules, features or platforms are combined? Which combinations do the tests cover? | Each option was tested alone; the combinations were not | nginx overflowing when map is used together with regular expressions; paths reachable only when a certain module is enabled | [32](../dimensions/32-configuration-and-defaults.md), [38](../dimensions/38-portability-and-build-context.md) |
| **Conservation and invariants** | What rules in the system say "the total never changes" or "this always holds"? Does every path (including optimized paths, batch paths and special types) maintain them? Is there an independent reconciliation as a backstop? | Invariants are written only in the design, with no code guarding them | A Bitcoin amount overflow created coins out of thin air; DeFi share rounding let the first depositor swallow the funds of later depositors | [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Conservation of totals"), [2.3](../questions.md#23-for-each-invariant-written-in-flow-documents-or-claimed-in-code-comments), [23](../dimensions/23-transactions-atomicity-and-consistency.md) ("Compensation and rollback"), [4.39](../specialties/4.39-payments-accounting-and-billing.md) ("Ledger invariants"), [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) ("Supply and double-spend checks") |
| **Uniqueness and single use** | Do things that must be "only one" or "used only once" (nonces, tokens, authorization codes, nullifiers, idempotency keys, sessions, order numbers, control streams that are unique per connection) really have only one valid value and really get used only once? After one is closed or freed, can another one be created? Can the same object be registered, queued, called back or finished twice? If the cleanup path creates new objects or allocates resources, can that trigger reclamation, timeouts or callbacks that come back and close the object that is already being closed? When a section, block, header or field that the format or protocol says appears only once appears again, is the whole thing replaced, is it rejected, or is only part of the state overwritten? | Uniqueness relies on convention, not enforcement | Several nullifiers derived from the same note; GCM nonce reuse; duplicate submissions causing duplicate charges; nginx HTTP/3 allowing another encoder stream to be opened after the first one was closed; nginx posting the same subrequest twice and finishing it twice, freeing the main request early; nginx HTTP/3 creating a new stream while closing a stream, which triggered connection reclamation, which closed the same stream again, recursing without end; the nginx mp4 module not rejecting duplicate atoms, so buffers and counts came from different instances | [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Uniqueness and single use"), [19](../dimensions/19-lifecycle-and-resources.md) ("Finishing twice", "Allocation in cleanup paths"), [4.3](../specialties/4.3-decoding-untrusted-external-data.md) ("Repeated structures"), [23](../dimensions/23-transactions-atomicity-and-consistency.md) |
| **Old valid versions accepted again** | Can things with valid signatures that are out of date (old firmware, old drivers, old tokens, old messages, old protocol versions, old configuration) be accepted again? What provides anti-rollback, anti-replay and anti-downgrade protection, and has revocation kept up? After the authoritative state changes (a password change, a removed role, a deleted account, a rotated key, withdrawn consent, ownership of an account proven for the first time), do the sessions, tokens, caches, replicas and derived grants already issued or copied out stop working too? | A signature only proves origin, not "latest"; revocation changes only the source, and nobody chases the copies already handed out | BlackLotus installing a signed vulnerable bootloader back; Windows Downdate rolling system components back to old versions; TLS downgrade attacks; old sessions and issued tokens still valid after a password change | [4.36](../specialties/4.36-embedded-firmware-and-real-time-constraints.md) ("Anti-rollback"), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Protocol state and replay"), [26](../dimensions/26-release-upgrade-migration-and-rollback.md), [4.5](../specialties/4.5-authentication-sessions-and-tokens.md) ("Revocation", "Pre-verification state", "Sensitive identity changes"), [28](../dimensions/28-authorization-and-access-control.md) ("Caching and invalidation"), [4.35](../specialties/4.35-client-apps-extensions-and-auto-update.md) ("Auto-update"), [30](../dimensions/30-privacy-data-governance-and-compliance.md) ("Whether deletion is real") |
