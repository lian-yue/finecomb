# Process

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Fixes and regressions** | Do fixed issues have regression tests? Does the fix only block the sample input? Is the same root cause still present at other entry points? **Which branches did the fix or refactor add, and which guards did it remove** (conditional compilation, macro switches)? Do the new branches get the same checks and tests? When one call is swapped for another (a lower-level primitive, another library function, inlining, splitting or merging helpers), does the new code still do the checks, locking, zeroing, counting and error conversion that the old call did as a side effect? When a value moves to another field or slot, or a field changes meaning, is every reader of the old place updated? | Fixes are made per report, not per root cause; the fix itself is rarely reviewed again; a check inside the replaced function is not "a deleted line", so it does not show up when reading the change | The first Log4j fix was bypassed; regreSSHion was the return of an 18-year-old vulnerability after a refactor removed a conditional compilation guard; the glibc syslog overflow came from a branch added by the fix for an earlier vulnerability; Linux binder swapped a copy helper that validated its input for a direct copy and lost the implicit offset alignment check | [41](../dimensions/41-test-quality.md) ("Regression protection for security fixes"), [5](../dimensions/5-coupling-and-blast-radius.md) ("Implicit duties of replaced calls", "Readers of a moved or redefined field"), [Part VI: Fix discipline](../report.md#part-vi-fix-discipline) |
| **The attacker's perspective** | Do the tests and the review take the side of a malicious party: forged input, one tampered field, one swapped binding value, one missing field, concurrency, replay, reordering, cancellation? When something is judged "not exploitable", is that based on evidence, or only on the shape of the input (restricted character set, short length)? Which other participants does the design assume are honest (the server a client connects to, peers, co-signers, provers, relays)? What happens if they lie, send a mode this side never enabled, or later contradict an earlier claim? | Participants are assumed to be honest by default | Circuits tested only with honest provers; authorization tested only on the success path; a vendor judged a bug not exploitable because the input "contains only dots and digits", when it was actually remote code execution (Ivanti CVE-2025-22457) | [41](../dimensions/41-test-quality.md) ("Tests from the attacker's side"), [Part V: Evidence levels](../report.md#part-v-evidence-levels-and-report-format), [27](../dimensions/27-security-and-trust-boundaries.md) ("Classifying input sources"), [4.2](../specialties/4.2-protocols-and-frame-parsing.md) ("Invalid input", "Messages for features that were not negotiated", "Claims a peer changes later"), [4.45](../specialties/4.45-blockchain-nodes-consensus-and-protocol-implementations.md) ("Peer-to-peer messages") |
