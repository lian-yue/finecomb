# Memory, lengths and parsing

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Length, offset and size calculations** | Where do the length, offset and capacity of each read and write come from? Can addition, subtraction or multiplication overflow or underflow? Is the remaining space checked before **every** write, with delimiters, escape sequences, prefixes and the trailing NUL counted too? Does the comparison use `<` or `<=`, and what happens when one more byte is written after the buffer is exactly full? Are the "length that should be written" and the "length actually written" mixed up? Do the pass that computes the size first and the pass that actually writes walk the same set, use the same test and encode the same way (escaping, variable-length integers, worst-case compressed length)? Between the two passes, can the computed value be evaluated again or changed elsewhere? | It only goes wrong for rare input combinations, boundary values or configurations | Heartbleed; Citrix Bleed treating the return value of `snprintf` as the actual length; an off-by-one comparison in OpenSSL punycode; glibc iconv checking capacity for only some control sequences; Linux uvcvideo skipping at write time a frame that was counted when computing the size; nginx reserving a fixed 4 bytes for a variable-length integer prefix when estimating length, while an overlong field actually needs 5 bytes; the nginx script engine re-running a regular expression between length estimation and copying, changing captures whose length was already computed | [14](../dimensions/14-boundaries-numbers-and-text.md) ("Capacity and boundary comparisons", "Where an offset lands"), [4.2](../specialties/4.2-protocols-and-frame-parsing.md), [C and C++](../lang-c-cpp.md) |
| **Parse cursors and input consumption** | In parsing, unescaping and tokenizing loops, how far does the cursor move at each step? On a malformed token, a repeated delimiter or a trailing escape character, can the cursor stay put, move back or run past the end? Can the same stretch of input be read twice and written into a buffer sized on the assumption that it is "read only once"? | With normal input, the cursor always moves forward by exactly the right amount | glibc `GLIBC_TUNABLES` consuming the same stretch twice when there is an extra `=` (Looney Tunables); a single trailing backslash in sudo making the loop run past the NUL | [14](../dimensions/14-boundaries-numbers-and-text.md) ("Parse cursors"), [4.2](../specialties/4.2-protocols-and-frame-parsing.md) |
| **Data layout assumptions** | Does the code assume the data is in contiguous memory, a single buffer, a single read or a fixed alignment, and is writable and owned only by itself? Could it actually be spread over several fragments, cross a boundary, be truncated, or be a shared page, a read-only page, a copy-on-write page or a duplicate mapping of the same page? Before writing in place, is it confirmed to be writable and exclusive? Is bookkeeping (free lists, chunk headers, lengths) kept inside the same buffer that receives outside data, where a write sized by outside values can land on it? | Common paths are always contiguous and exclusive; only a few paths produce fragments or sharing | Linux ebtables SNAT writing into a non-linear skb fragment backed by file pages; io_uring treating duplicate mappings of the same page as physically contiguous (CVE-2023-2598) | [14](../dimensions/14-boundaries-numbers-and-text.md) ("Data layout", "Bookkeeping kept inside data buffers", "Where an offset lands"), [4.2](../specialties/4.2-protocols-and-frame-parsing.md) ("Message boundaries"), [4.30](../specialties/4.30-os-interfaces-system-calls-and-descriptors.md) |
| **Lifetime and ownership** | Who creates, holds and frees this object? After it is freed, who still holds a reference (callbacks, timers, async tasks, caches, secondary indexes, another connection, pages mapped to user space, pointers in temporary buffers)? Is it allocated from a memory pool, arena or scope but attached to an object that lives longer? Do error paths free twice or miss a free? In the same batch or transaction, can a later step still get an object that an earlier step deleted or invalidated? Can the error path of one item change, free or reset other items in the same batch that nobody examined? | Normal paths are paired; async, batch or error paths are not | nginx HTTP/3 allocating a session-level buffer in a single stream's memory pool, so the buffer was freed when the stream closed while the pointer remained; use-after-free in nginx SSI and the OCSP parser; use-after-free in Linux nf_tables and kTLS; GPU mappings still usable after the pages were freed | [19](../dimensions/19-lifecycle-and-resources.md) ("Objects invalidated within a batch", "Allocation ownership", "Scope of error handling in a batch"), [12](../dimensions/12-state-machines-and-transitions.md), [C and C++](../lang-c-cpp.md) |
| **Keeping linked fields in sync** | When a group of fields that must hold together (buffer and length, array and count, pointer and valid flag, data and version number, cache and expiry time) is reallocated, reset, copied, inherited, partly fails or is truncated to a limit, are they updated together? Is there a path that changes only half of them? | Each field is maintained when looked at alone | nginx reallocating the capture array for a subrequest without clearing the capture count, then reading uninitialized memory by the old count; nginx mail authentication rewriting the data pointer before a decode failure, leaving "new data, old length"; a struct copy carrying along a pointer that should not be shared | [5](../dimensions/5-coupling-and-blast-radius.md) ("Linked invariants"), [16](../dimensions/16-language-and-runtime-pitfalls.md) ("Values, references and aliasing"), [19](../dimensions/19-lifecycle-and-resources.md), [14](../dimensions/14-boundaries-numbers-and-text.md) ("Failure midway through parsing") |
