# State, timing and paths

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Concurrency and interleaving** | Can the same object be reached by two execution flows at once (two writers, a read and a write at the same time, before and after a suspension point)? Can something get in between the check and the use? Can the intermediate state of a multi-step flow be exploited by concurrent requests? | The contract did not say "only one writer is allowed", and the implementation did not block it either | Linux AF_ALG allowed two writers to interleave, hidden for 14 years; a race between the limit check and the deduction; a race in the email verification flow | [18](../dimensions/18-concurrency-and-memory-model.md), [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Timing and races") |
| **Assumptions broken by callbacks and reentrancy** | After a check, specialization or caching, was a callback, getter, user code or external contract called in between, or was there a write through an alias? Do the earlier assumptions (type, length, balance, permission, state) still hold? Are they checked again afterwards? If the context switched in the middle of processing (switching configuration by SNI, upgrading the protocol, switching tenant or account), are sizes, counts and permissions computed under the old context still usable? When the same value is evaluated twice, are the two results guaranteed to be the same? In the other direction, when a library, framework or engine calls back into our code, does our code replace or modify the context, configuration or collection that the caller is using? Does the caller's contract allow that? | The check and the use are in the same function and look "right next to each other"; the author of a callback only looks at their own side | V8 optimized code kept running with the old type after a callback changed the object; a contract updating the balance only after an external call (reentrancy); nginx switching configuration by SNI in the TLS handshake callback, allocating the extension array by the count before the switch and processing it by the count after the switch | [18](../dimensions/18-concurrency-and-memory-model.md) ("Lock granularity and behavior while holding a lock"), [35](../dimensions/35-dependencies.md) ("Understanding the contract"), [4.27](../specialties/4.27-interpreters-compilers-and-virtual-machines.md) ("Assumptions behind speculative optimization"), [4.38](../specialties/4.38-smart-contracts-and-on-chain-interaction.md) ("Reentrancy") |
| **States and phases** | In each state, can each entry point be called? Can phases such as initialization, installation, upgrade, shutdown, reconnection, and before and after authentication be reentered, skipped or run out of order? | The design only drew the normal order | The setup wizard can still be called again after it is finished; connection protocol messages were handled before authentication finished (Erlang/OTP SSH) | [12](../dimensions/12-state-machines-and-transitions.md), [9](../dimensions/9-business-logic-and-flow-integrity.md) |
| **Choosing after seeing** | Can one party make or change a choice after it sees a value that the choice should have been fixed before? A prover picks what it sends after seeing the challenge; a participant submits, withdraws, aborts or retries after seeing a random result, a price, an opponent's bid or a pending transaction. When a challenge, random number or result is derived, is every input the other side can influence fixed in advance and included in the calculation? When the result is unfavorable, can the whole operation be made to fail, roll back and start over? Is the commitment itself checked to be binding (valid, accepted, impossible to replace) before anything is revealed? When several proofs or commitments are checked together in one combined equation, is each one still bound on its own? | Each step is legal on its own; the problem is the order: who fixes first and who sees first | A value in a zero-knowledge proof left out of the challenge calculation, so the prover picked it after seeing the challenge and forged a proof; a block producer discarding a block-hash random number that is bad for it; a contract calling on-chain randomness and reverting when the result is unfavorable | [4.44](../specialties/4.44-zero-knowledge-proofs-and-circuits.md) ("Challenges and transcripts"), [4.41](../specialties/4.41-defi-economics-and-oracles.md) ("Front-running and transaction ordering"), [9](../dimensions/9-business-logic-and-flow-integrity.md) ("Commit before reveal"), [Move](../lang-move.md) ("Composing randomness and gas"), [Solidity](../lang-solidity.md) ("Randomness"), [4.4](../specialties/4.4-cryptography-and-credentials.md) ("Batched and aggregated verification") |
| **Leftovers after cancellation and interruption** | After an operation is cancelled, times out, disconnects or exits abnormally midway, what state are the shared connections, buffers, locks, pooled objects and partly written state in? Can the next user (possibly a different user) go on to read what the previous one left behind? | Cancellation paths are rarely tested | After a redis-py command was cancelled, the connection was still reused, and ChatGPT showed users the titles of other people's conversations | [4.1](../specialties/4.1-networking-and-connections.md) ("Connection state after cancellation"), [10](../dimensions/10-apis-and-contracts.md) ("View lifetime"), [19](../dimensions/19-lifecycle-and-resources.md), [25](../dimensions/25-crash-and-recovery.md) |
| **Shared state across trust levels** | Can untrusted input, a plugin, a sandboxed script or a previous request change state shared by the whole process or by later requests: environment variables, the current directory, umask, locale, global configuration, singletons, class attributes and prototypes, module caches, thread-local variables reused by thread pools, the session settings of pooled connections? Can more trusted code, or another user's request, read that state later? | Shared state is not in any interface parameter, and reviews follow data only through parameters | A script in a trusted mode changing the process's PATH, so later privileged operations found programs through it; a deep merge writing external keys into the object prototype, affecting every object in the process; a pooled connection reused with the previous user's session settings | [4.27](../specialties/4.27-interpreters-compilers-and-virtual-machines.md) ("Process-wide state", "Run state isolation"), [4.47](../specialties/4.47-local-privileged-components-and-local-privilege-escalation.md) ("Caller-controlled environment"), [27](../dimensions/27-security-and-trust-boundaries.md) ("Shared state that less trusted parties can change"), [JavaScript](../lang-javascript.md) ("Prototype pollution") |
| **Interpreting failures and special values** | How does the caller interpret each failure, error code and special return value (zero, negative, empty, sentinel value)? Is a three-state result tested as true or false? When one integer encodes several things at once (bit fields, a verdict plus an error code), do the producer and the consumer agree on the value range and how it is split? Can a failure end up treated as success and carry on? Can the other side deliberately cause this failure (exhaust memory, fill a queue, trigger a timeout)? When several checks write the same result, can the success of a later step turn the failure of an earlier step back into success? In the other direction, can the other side deliberately send a value that has a special meaning to us (a sentinel value, a pseudo-handle, a reserved key name or field, a wildcard, zero, -1, the maximum value, an empty name), which is then accepted and used as an ordinary value? | The caller only handled the few return values it thought of; special values are treated as something only our own code produces | GnuTLS reporting a verification failure as success; OpenSSH treating only -1 as failure, so an attacker exhausted memory to produce -2 and bypass host key verification; one verdict value in nf_tables interpreted differently by different layers | [13](../dimensions/13-error-handling-and-failure-semantics.md) ("Errors read as success", "Failures overwritten by later steps"), [29](../dimensions/29-fail-safe-behavior-and-dangerous-operations.md), [4.30](../specialties/4.30-os-interfaces-system-calls-and-descriptors.md) ("Handles and capabilities passed across boundaries"), [4.22](../specialties/4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md) ("Object graph deserialization") |
| **Fallbacks and rarely taken paths** | When the main path does not apply and the code takes a fallback, catch-all, degraded path, slow path or "no match" branch, were the lengths, states and results it uses computed on every path that leads there? Or does it use initial values? Do empty values, zero-length values, single elements and the first item from a cache or queue go through the same validation and constraints as ordinary values? | Tests always take the main path and ordinary values | glibc syslog's fallback branch allocating a buffer by the initial value 0; OpenSSL reading the first item when the client list is empty (CVE-2024-5535); kTLS not setting this call's content type on a zero-length first record from the cache queue (CVE-2025-39682) | [13](../dimensions/13-error-handling-and-failure-semantics.md) ("Fallback branches"), [14](../dimensions/14-boundaries-numbers-and-text.md) ("Empty and missing") |
