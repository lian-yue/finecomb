# Root-cause facets

Root-cause facets are questions distilled from the root causes of real vulnerabilities, independent of domain and language. The same facet shows up again and again in kernels, web servers, cryptography libraries, smart contracts and business systems, only in a different shape. The [general dimensions](dimensions/index.md) are organized by quality attribute and the [specialties](specialties/index.md) by target type, and either one can let a cross-domain root cause fall through the gaps. This file pulls the root causes out on their own: **go through them for every object**.

How to use:

- After the [per-object questions](questions.md), ask every facet in turn for each entry point, validation point, piece of shared state, buffer, parsing loop, state transition and external interaction. When a facet does not apply to an object, write down the reason in the coverage record.
- The "Detailed criteria" column of each facet points to the specific check rows. This file only gives the question to ask and why it is easy to miss.
- "Real cases" only show what the facet looks like. They are not a checklist; the same facet holds in other domains too.
- Group the issues you find by facet. This also works as a reverse check: if a facet was never seriously asked during the whole review, that is a coverage gap.
- This checklist has been tested for hits against real vulnerabilities (nginx, the Linux kernel, OpenSSL, OpenSSH, glibc, major frameworks and enterprise appliances, on-chain and zero-knowledge proof incidents), and every root cause it missed has been turned into a facet here. Check new vulnerabilities the same way: if no facet matches, a facet needs to be added.

| **Authority beyond the job** | Does each credential, identity, token, service account, database user, container, process and agent tool hold only the permissions its job needs? ## Representation and transformation

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Multiple representations of the same fact** | Does the same value, path, identity or encoding have more than one way to write it? Is the form used for validation the same as the form finally used? Does writing it out and reading it back give the original value? Do the side that escapes or validates and the side that finally interprets split the input into characters and tokens with the same character encoding and the same rules (multibyte encodings, quoting rules, dialects)? | Two components are each "correct", but understand the input differently when combined | Paths validated before decoding; an array parameter sending the reset email to a second address; both x and x plus the modulus pass verification; Git writing configuration without quotes and dropping the carriage return when reading it back | [27](dimensions/27-security-and-trust-boundaries.md) ("Parser differentials"), [24](dimensions/24-encoding-and-persistent-formats.md) ("Round trip and canonical form"), [4.17](specialties/4.17-templates-and-text-output.md) ("Escaping under multibyte encodings") |
| **Transformations after validation** | After validation, does the value still go through decoding, normalization, character set conversion, command-line reassembly, template expansion or another parser? Is what validation sees the same as what finally runs? | Validation and use are in two places, and no one watches the transformation in between | Windows best-fit character set mapping turns a soft hyphen into `-` (PHP-CGI); calling a batch file with an argument array is still re-parsed by `cmd.exe` (BatBadBut) | [4.22](specialties/4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md) ("Windows command-line reassembly", "Character set conversion rewriting arguments"), [27](dimensions/27-security-and-trust-boundaries.md) ("Input validation") |
| **Processing path chosen by input** | Is the parser, handler or branch chosen by an attribute the request controls (content type, extension, parameter, version number)? | **Data turning into instructions** | Which places that interpret external data will it finally reach (queries, commands, templates, expressions, protocol headers, configuration, log lookups, next-hop requests, line-based internal protocols)? Is it stored somewhere first along the way and later spliced in elsewhere? | The first use is safe; protection is lost on second use or forwarding | Log4Shell; a session ID becomes a file name and then goes into a shell; nginx injecting request content into upstream or mail authentication requests; newline injection into memcache commands | [27](dimensions/27-security-and-trust-boundaries.md) ("Injection surface", "Second-order use"), [4.22](specialties/4.22-subprocesses-dynamic-execution-and-decoder-side-effects.md), [4.17](specialties/4.17-templates-and-text-output.md) ("Boundaries at the insertion point"), [4.7](specialties/4.7-databases-and-queries.md) ("Connection strings and driver parameters"), [4.15](specialties/4.15-command-line-and-process-entry-points.md) ("Implicit expansion by argument-parsing libraries") |
| **Protocol and format conversion** | When converting between two protocols, two encodings or two versions, which semantics are lost and which new semantics are introduced? Is a character that is legal in the first one a delimiter in the second? Do upstream and downstream agree on terminators and lengths? Do both sides agree whether a write is an incremental change or a full replacement? When only the changes are synced into a copy that gets overwritten as a whole, can the unchanged parts be lost, or deleted things come back? | Each protocol is right on its own; no one owns the conversion layer | Injection when HTTP/2 requests are converted to HTTP/1 for the upstream; after a proxy removes hop-by-hop headers, the backend trusts the request as local; SMTP smuggling | [4.14](specialties/4.14-server-request-handling-and-middleware.md), [4.2](specialties/4.2-protocols-and-frame-parsing.md), [37](dimensions/37-interoperability-and-coexistence.md), [23](dimensions/23-transactions-atomicity-and-consistency.md) ("Incremental sync into a copy that is overwritten whole"), [4.6](specialties/4.6-caching-and-storage.md) ("Deletion and resurrection") |
| **Which attributes survive a move** | When an object is copied, unpacked, mounted, imported, converted, saved as another file, forwarded or mapped across namespaces, are **restricting attributes** (download origin marks, taint, data classification, quarantine attributes) kept, and are **privilege attributes** (setuid, capabilities, owner, signed status) stripped or checked again? Can boundary values (unmapped users, default identities) fall into a special case that "neither errors nor strips"? If a mark cannot be written, is the object still let through? In multi-step chains (redirects, forwarding, delegation, privilege dropping), does the stripping or narrowing done at an earlier step still hold at every later step? | **Completeness of equivalence checks** | Does every judgment that "these two are the same, so we can skip, merge, reuse or prune" (equality comparisons, cache keys, deduplication keys, memoization, state merging, verifier pruning) include every field that affects the result and security? | **Consistency of types and tags** | In how many places is the type of the same field or object declared (struct definition, encoding and decoding template, comparison, copy, free, union tag)? ## Memory, lengths and parsing

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Length, offset and size calculations** | Where do the length, offset and capacity of each read and write come from? Can addition, subtraction or multiplication overflow or underflow? Is the remaining space checked before **every** write, with delimiters, escape sequences, prefixes and the trailing NUL counted too? Does the comparison use `<` or `<=`, and what happens when one more byte is written after the buffer is exactly full? Are the "length that should be written" and the "length actually written" mixed up? Do the pass that computes the size first and the pass that actually writes walk the same set, use the same test and encode the same way (escaping, variable-length integers, worst-case compressed length)? Between the two passes, can the computed value be evaluated again or changed elsewhere? | It only goes wrong for rare input combinations, boundary values or configurations | Heartbleed; Citrix Bleed treating the return value of `snprintf` as the actual length; an off-by-one comparison in OpenSSL punycode; glibc iconv checking capacity for only some control sequences; Linux uvcvideo skipping at write time a frame that was counted when computing the size; nginx reserving a fixed 4 bytes for a variable-length integer prefix when estimating length, while an overlong field actually needs 5 bytes; the nginx script engine re-running a regular expression between length estimation and copying, changing captures whose length was already computed | [14](dimensions/14-boundaries-numbers-and-text.md) ("Capacity and boundary comparisons", "Where an offset lands"), [4.2](specialties/4.2-protocols-and-frame-parsing.md), [C and C++](lang-c-cpp.md) |
| **Parse cursors and input consumption** | In parsing, unescaping and tokenizing loops, how far does the cursor move at each step? On a malformed token, a repeated delimiter or a trailing escape character, can the cursor stay put, move back or run past the end? Can the same stretch of input be read twice and written into a buffer sized on the assumption that it is "read only once"? | With normal input, the cursor always moves forward by exactly the right amount | glibc `GLIBC_TUNABLES` consuming the same stretch twice when there is an extra `=` (Looney Tunables); a single trailing backslash in sudo making the loop run past the NUL | [14](dimensions/14-boundaries-numbers-and-text.md) ("Parse cursors"), [4.2](specialties/4.2-protocols-and-frame-parsing.md) |
| **Data layout assumptions** | Does the code assume the data is in contiguous memory, a single buffer, a single read or a fixed alignment, and is writable and owned only by itself? Could it actually be spread over several fragments, cross a boundary, be truncated, or be a shared page, a read-only page, a copy-on-write page or a duplicate mapping of the same page? Before writing in place, is it confirmed to be writable and exclusive? Is bookkeeping (free lists, chunk headers, lengths) kept inside the same buffer that receives outside data, where a write sized by outside values can land on it? | Common paths are always contiguous and exclusive; only a few paths produce fragments or sharing | Linux ebtables SNAT writing into a non-linear skb fragment backed by file pages; io_uring treating duplicate mappings of the same page as physically contiguous (CVE-2023-2598) | [14](dimensions/14-boundaries-numbers-and-text.md) ("Data layout", "Bookkeeping kept inside data buffers", "Where an offset lands"), [4.2](specialties/4.2-protocols-and-frame-parsing.md) ("Message boundaries"), [4.30](specialties/4.30-os-interfaces-system-calls-and-descriptors.md) |
| **Lifetime and ownership** | Who creates, holds and frees this object? After it is freed, who still holds a reference (callbacks, timers, async tasks, caches, secondary indexes, another connection, pages mapped to user space, pointers in temporary buffers)? Is it allocated from a memory pool, arena or scope but attached to an object that lives longer? Do error paths free twice or miss a free? | **Keeping linked fields in sync** | When a group of fields that must hold together (buffer and length, array and count, pointer and valid flag, data and version number, cache and expiry time) is reallocated, reset, copied, inherited, partly fails or is truncated to a limit, are they updated together? Is there a path that changes only half of them? | Each field is maintained when looked at alone | nginx reallocating the capture array for a subrequest without clearing the capture count, then reading uninitialized memory by the old count; nginx mail authentication rewriting the data pointer before a decode failure, leaving "new data, old length"; a struct copy carrying along a pointer that should not be shared | [5](dimensions/5-coupling-and-blast-radius.md) ("Linked invariants"), [16](dimensions/16-language-and-runtime-pitfalls.md) ("Values, references and aliasing"), [19](dimensions/19-lifecycle-and-resources.md), [14](dimensions/14-boundaries-numbers-and-text.md) ("Failure midway through parsing") |

## State, timing and paths

| Facet | Question to ask | Why it is often missed | Real cases | Detailed criteria |
| --- | --- | --- | --- | --- |
| **Concurrency and interleaving** | Can the same object be reached by two execution flows at once (two writers, a read and a write at the same time, before and after a suspension point)? Can something get in between the check and the use? Can the intermediate state of a multi-step flow be exploited by concurrent requests? | The contract did not say "only one writer is allowed", and the implementation did not block it either | Linux AF_ALG allowed two writers to interleave, hidden for 14 years; a race between the limit check and the deduction; a race in the email verification flow | [18](dimensions/18-concurrency-and-memory-model.md), [9](dimensions/9-business-logic-and-flow-integrity.md) ("Timing and races") |
| **Assumptions broken by callbacks and reentrancy** | After a check, specialization or caching, was a callback, getter, user code or external contract called in between, or was there a write through an alias? Do the earlier assumptions (type, length, balance, permission, state) still hold? Are they checked again afterwards? If the context switched in the middle of processing (switching configuration by SNI, upgrading the protocol, switching tenant or account), are sizes, counts and permissions computed under the old context still usable? When the same value is evaluated twice, are the two results guaranteed to be the same? In the other direction, when a library, framework or engine calls back into our code, does our code replace or modify the context, configuration or collection that the caller is using? Does the caller's contract allow that? | The check and the use are in the same function and look "right next to each other"; the author of a callback only looks at their own side | V8 optimized code kept running with the old type after a callback changed the object; a contract updating the balance only after an external call (reentrancy); nginx switching configuration by SNI in the TLS handshake callback, allocating the extension array by the count before the switch and processing it by the count after the switch | [18](dimensions/18-concurrency-and-memory-model.md) ("Lock granularity and behavior while holding a lock"), [35](dimensions/35-dependencies.md) ("Understanding the contract"), [4.27](specialties/4.27-interpreters-compilers-and-virtual-machines.md) ("Assumptions behind speculative optimization"), [4.38](specialties/4.38-smart-contracts-and-on-chain-interaction.md) ("Reentrancy") |
| **States and phases** | In each state, can each entry point be called? Can phases such as initialization, installation, upgrade, shutdown, reconnection, and before and after authentication be reentered, skipped or run out of order? | The design only drew the normal order | The setup wizard can still be called again after it is finished; connection protocol messages were handled before authentication finished (Erlang/OTP SSH) | [12](dimensions/12-state-machines-and-transitions.md), [9](dimensions/9-business-logic-and-flow-integrity.md) |
| **Choosing after seeing** | Can one party make or change a choice after it sees a value that the choice should have been fixed before? A prover picks what it sends after seeing the challenge; a participant submits, withdraws, aborts or retries after seeing a random result, a price, an opponent's bid or a pending transaction. When a challenge, random number or result is derived, is every input the other side can influence fixed in advance and included in the calculation? When the result is unfavorable, can the whole operation be made to fail, roll back and start over? Is the commitment itself checked to be binding (valid, accepted, impossible to replace) before anything is revealed?
