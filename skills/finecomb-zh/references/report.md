# 报告与修复

## 五、证据等级与报告格式

每条问题记录分别标明证据等级和严重性。以下证据口径同样适用于安全漏洞、正确性缺陷和文档问题：

| 等级 | 含义 |
| --- | --- |
| **实测** | 在记录的源码、配置和环境下有可复现输入与可观察结果；模拟、替身或隔离复现须写明与真实环境的差别 |
| **静态确证** | 所需输入、前提和可达路径均已核实，代码与契约足以确定结果；不代表已完成线上利用或实测影响规模 |
| **待验证** | 缺少关键前提、可达性、环境或结果证据，说明还差什么；单独列出，不计入已确认问题数量 |

严重性按实际影响、可利用条件、影响范围和恢复代价评估，不按漏洞名称或工具标签自动定级；缺少某种防护本身也不必然是高风险。项目有已确认分级标准时按其标准执行，否则使用：

| 级别 | 判据 |
| --- | --- |
| **严重** | 可导致大范围系统控制、重大资产或机密损失等严重后果，且所需条件在审查场景中成立，需要立即处置 |
| **高** | 可导致实质越权、敏感数据泄漏、重要数据损坏或持续服务中断，影响与可达条件有证据支撑 |
| **中** | 影响或触发条件受限，但仍破坏正确性、安全目标或可用性 |
| **低** | 影响较小的确定缺陷；纯风格选择、一般加固建议与未证明的担忧另列，不冒充漏洞 |

需要 CVSS、CWE 或外部标准映射时，给出所用版本、向量或条目标识及依据；分类标签不能替代根因与可达性证据。

每条按这个形状写：

| 字段 | 内容 |
| --- | --- |
| 标识与位置 | 稳定问题标识，`文件:行`、函数或配置入口 |
| 现象与根因 | 预期行为、实际行为，哪条契约或安全目标被破坏 |
| 触发条件 | 所需身份、输入、配置、执行顺序和环境；安全问题补攻击者能控制什么 |
| 证据 | 来源到结果的路径、相关守卫为何未阻断、最小复现输入或静态推导；实测附精确命令、退出状态与必要输出 |
| 影响 | 影响对象、范围、成本和恢复条件；潜在扩大影响与已证明结果分开 |
| 建议 | 最小修复位置及受影响调用方，验收应观察什么；范围外改动单独说明 |
| 等级 / 证据 / 状态 | 例如高 / 静态确证 / 未修复；已修复但未验证时明确写出 |

整体报告包含：

- **结论与范围**：审查对象、基线、已核实配置、排除项，以及按严重性排序的已确认问题；没发现问题只能表述为「在已审范围和条件下未发现已确认问题」。
- **覆盖记录**：按所选规模列出通用维度、对象与专项，状态区分「已查并发现问题」「已查未发现」「部分检查」「未检查」「不适用」。未完成项写原因和缺失证据，不适用项写实际依据；相同状态可合并列举，机制表的命中归入对应项即可。
- **验证记录**：执行或复用的精确入口、输入身份和结果；明确区分本次通过、缓存复用、失败、零匹配、跳过、超时、环境错误和未运行。扫描附工具版本、规则或漏洞库日期、配置和排除项。
- **变更与遗留**：哪些已修复、哪些验证通过、哪些未改及原因。区分「既有」「本次引入」「来源未确认」；没有可比基线时采用最后一种，不临时还原工作区来猜测。

**去重与披露**：同一根因及同一修复点合并为一条，列全受影响入口与后果；不同根因分别记录，组合攻击用引用串联。已知问题或误报必须有当前证据，不能仅凭旧标签关闭。报告中的账号、凭据、用户数据和可访问地址按需脱敏，对外发送按已确认授权和项目披露流程执行。

## 六、修复纪律

只有修复已获授权时进入本节。修改范围、兼容清理、测试编写、验证次数和文档同步统一按[目标项目的硬边界](scope.md#目标项目的硬边界)，这里仅补审查结果如何落实。

1. 先说明根因、影响与最小修复点；在执行敏感操作的权威层修复，不只挡住某个样例输入或界面入口。范围内的等价可达路径一并核对，范围外迁移项只报告。
2. 验收对准原问题的成功、拒绝和真实失败行为，尤其检查拒绝后没有不应发生的副作用。测试能否抓到问题按[41](dimensions.md#41-测试质量)判断，不要求默认执行变异测试或反复关闭守卫。
3. 按选定的最小入口完成验证后更新原问题状态，区分修复完成、验证完成和剩余边界；缓解措施只挡住部分路径时，说明残余风险，不能直接写成根因已消除。
4. 修复本身也是一次改动：按[规模自适应](scope.md#规模自适应)的「审这次改动」过一遍五张追问清单，确认没有引入新问题；多轮修复的收敛判据见[大目标分片与多轮审查](scope.md#大目标分片与多轮审查)。
