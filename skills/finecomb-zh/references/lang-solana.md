# A.14 Solana 程序（Rust 与 Anchor）

| 检查点 | 什么算问题 |
| --- | --- |
| **账户所有者校验** | 传入账户的所有者程序没有校验，攻击者可以传入自己伪造的数据账户 |
| **签名者校验** | 需要授权的操作没有检查对应账户是否签了名 |
| **账户身份与替换** | 系统账户、sysvar、程序账户没有校验真实地址，可以被伪造的账户替换（Wormhole 2022 年因未校验指令 sysvar 账户，被伪造出已验证的签名，损失约 3.2 亿美元） |
| **账户关联链** | 只校验了账户之间相邻的一层关联（A 记录了 B，B 记录了 C），链条的起点没有落到可信的根；攻击者可以伪造整条链（Cashio 2022 年因此被用伪造的抵押账户铸币） |
| 剩余账户 | `remaining_accounts` 不经过 Anchor 的约束检查，程序是否自己校验了每个账户的所有者、类型和身份 |
| 派生地址的种子 | 派生地址（PDA）的种子没有包含足够的区分字段，不同用户或用途会撞到同一地址；没有使用规范的 bump |
| 跨程序调用 | 被调用程序的 ID 没有校验；签名权限经跨程序调用传给了不可信的程序 |
| 跨程序调用后的数据 | 跨程序调用改了账户后，程序手里反序列化出的旧副本不会自动刷新（Anchor 要调用 `reload()`），之后的检查用的是旧数据 |
| 账户重复 | 同一个账户被同时作为两个参数传入（如转出方与转入方相同），导致余额计算错误 |
| 账户关闭与复活 | 关闭账户后数据没有清零；租金退回后，同一笔交易里又给它充值，账户「复活」 |
| 重复初始化 | `init_if_needed` 或手写的初始化没有拦住已初始化的账户，所有者等字段能被重新写入 |
| Token-2022 扩展 | 转账手续费、转账钩子、永久代理、默认冻结、机密转账等扩展改变了转账语义；程序是只接受经典代币程序，还是按扩展处理实际到账数额；代币程序 ID 是否校验 |
| 指令内省 | 用指令 sysvar 检查同一交易里的其它指令时，是否按绝对下标定位并校验程序 ID；攻击者能否插入额外指令让位置错开 |
| **验签预编译的偏移字段** | 用指令内省确认交易里有 Ed25519 或 secp256k1 验签指令时，是否解析这条指令里的签名、公钥、消息偏移和指令下标，并确认它们指向程序自己核对的那几段；按固定位置读公钥和消息，而验签程序按偏移验的是另一段，就等于没验证是谁签的 |
| 程序升级权限 | 程序是否可升级，升级权限由谁持有；可升级程序托管的资产，实际上交给了升级权限的持有者 |
| 持久随机数交易 | 使用持久随机数的交易不会因区块哈希过期而失效，签好后可以在很久以后提交；多签或管理操作用这种交易预先签名时，签名者签下的是一张长期有效的授权（另见[4.43](specialties.md#443-钱包签名与链下组件)「预签名与长期有效的签名」） |
| 类型混淆 | 不同类型的账户数据没有判别字段，一种账户能被当成另一种解析 |
| 整数 | 发布构建默认不检查溢出；应使用带检查的运算 |
| 计算预算与空间 | 计算单元上限导致操作无法完成；账户空间与租金不足 |
| Anchor 约束 | `#[account(...)]` 的约束写漏（`has_one`、`seeds`、`owner`、`signer`）；使用 `UncheckedAccount` 的理由有没有写明 |
